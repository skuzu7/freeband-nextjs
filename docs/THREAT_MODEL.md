# Threat Model: Authentication & Session Architecture

**Project:** `freeband-nextjs`  
**Target Component:** Administrative Authentication, Session Management, and Media Proxy  
**Methodology:** STRIDE (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege)

---

## 1. System Overview & Boundaries

The administrative area provides media asset management and performance updates. All administrative endpoints and Server Actions are protected by a cryptographic session verification layer (`src/lib/session.ts`) coupled with Next.js middleware and secure HTTP cookies.

```
[ Client Browser ]
        │  ▲
        │  │  Cookie: admin_session (HttpOnly; Secure; SameSite=Lax)
        ▼  │
[ Next.js Edge / Node.js Runtime ]
        │
        ├──► verifySession(token, secret) ──► HMAC-SHA256 & TimingSafe Check
        │
        ├──► Admin Server Actions (src/app/admin/actions.ts)
        │
        └──► Media Proxy (src/proxy.ts) ──► Host & Header Sanitization
```

---

## 2. STRIDE Threat Analysis & Defensive Mitigations

| STRIDE Category | Identified Threat Vector | Architectural Mitigation | Verifiable Test / Implementation |
| :--- | :--- | :--- | :--- |
| **Spoofing (S)** | Forging admin session cookies or presenting legacy unauthenticated tokens (e.g. static `"1"`). | Session tokens are cryptographically bound via `expiry.signature` using HMAC-SHA256. | `src/lib/__tests__/session.test.ts` (`"rejects the legacy forgeable cookie value"`) |
| **Tampering (T)** | Modifying token timestamp to artificially extend session expiration. | Expiry timestamp is included in the HMAC payload; modifying timestamp invalidates the signature. | `src/lib/__tests__/session.test.ts` (`"rejects a tampered expiry"`) |
| **Repudiation (R)** | Unaudited administrative mutations or unauthenticated state changes. | Server actions re-verify active session state on every invocation before data mutations. | `src/app/admin/actions.ts` |
| **Information Disclosure (I)** | Exposing session secrets via client-side JavaScript execution (XSS) or timing side channels. | Cookies set with `httpOnly: true`, `secure: true` (in production), `sameSite: "lax"`. Constant-time comparison using `crypto.timingSafeEqual`. | `src/lib/session.ts` (`sessionCookieOptions()`, `secretsMatch()`) |
| **Denial of Service (D)** | Brute-force credential guessing against admin login. | Authentication attempts enforce rate-limiting patterns and constant-time failure handling. | `src/app/admin/actions.ts` |
| **Elevation of Privilege (E)** | Bypassing client-side route guards to trigger administrative actions directly. | All security boundaries are enforced strictly server-side inside Server Actions and API handlers. | `src/app/admin/actions.ts` |

## 3. Cryptographic Primitives & Design Choices

1. **HMAC-SHA256 over Vanilla Hashing:** Plain hashes without secret-key binding can be generated by any client possessing the target payload. HMAC-SHA256 ensures that only the server holding `SESSION_SECRET` can create valid signatures.
2. **Double-HMAC Timing Equalizer:** To prevent timing leakage when comparing strings of varying lengths or content, secrets are converted to fixed-length HMAC digests before invoking `crypto.timingSafeEqual`.
3. **Deterministic Expiration:** Stored sessions do not rely on server-side memory caches; expiry is encoded directly into the verifiable payload, minimizing operational denial-of-service attack surface.
